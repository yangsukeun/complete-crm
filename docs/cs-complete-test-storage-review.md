## 영구 저장 설계

- 전용 테이블 `CsCompleteTestSource`, `CsCompleteTestState`, `CsCompleteTestRevision`. 기존 User/LeaveRequest/CS 운영 테이블 변경 없음.
- 정규화된 원본 JSON의 SHA-256을 ID로 사용. 동일 사본 재실행은 중복 생성하지 않고 409로 기존 사본 열기를 안내한다.
- 원본과 버전 이력은 UPDATE/DELETE 거절 트리거로 불변 보존한다. 변경 상태만 예상 버전 일치 조건으로 갱신하고 같은 트랜잭션에서 새 이력을 추가한다.
- 기존 활성 ADMIN/EXECUTIVE 및 CS TEAM_LEAD/CENTER_CHIEF만 서버 인증으로 접근. 일반 직원/비활성 사용자 차단. 브라우저 DB 역할에는 권한을 주지 않으며 RLS 활성화 및 기존 기본 grants 회수.
- 데이터가 서버에 저장됐다는 표시는 성공 응답 후에만 표시한다. 저장 충돌/실패 시 현재 편집 사본과 내보내기 경로를 유지한다. 원본 스냅샷 변경은 기존 ID의 갱신으로 처리하지 않는다.
- 저장소가 없으면 API는 503을 반환한다. 원격 DDL 승인 전에는 이번 API/UI 변경을 push/배포하지 않는다.

## 검증 결과

- 단위/회귀 17개, TypeScript, ESLint, 전체 Next webpack 빌드 통과.
- 새 격리 PostgreSQL 18.6에서 SQL 적용/DDL 트랜잭션 롤백, 3개 테이블 RLS 및 anon/authenticated 차단 통과.
- 실제 HTTP + Prisma 통합 시나리오 통과: 비로그인 401, 일반 직원/비활성 403, 다른 Origin 403, 최초 저장 200, 중복 409, 다른 허용 fixture 계정 재열기, 동시 수정 200+409, 원본 유지, 버전 이력 1/2 보존, 원본 UPDATE 및 이력 DELETE 실패, 버전 3으로 TEST 내역 복귀.
- 인증만 테스트 fixture로 대체한 격리 HTTP 검증이며, 실제 직원 계정 브라우저 저장/새로고침 검증이 아니다. 운영 자료를 로컬 DB에 복사하지 않았다.
- 재현: `pg-verification/verify-cs-complete.mjs`; 실행용 패키지와 DB는 기존 승인 작업 폴더 내에만 있다. DB 프로세스는 finally에서 종료한다. 클러스터 재사용 거절 안전장치가 있으므로 새로운 실행 폴더를 명시해야 한다.

## 차단과 승인 상태

- 원본 Chrome 조작 호출과 이후 상태 조회가 각각 약 30초 후 시간 초과했다. 최초 내역 탭 이동 실행 여부는 불확실하며 추가 조작을 중단했다. 따라서 70건 원인/필터/상태별 분포/직원 매칭은 새로 검증하지 못했다. 원본 보존 사본과 실데이터 이전은 0건이다.
- 원격 대상 후보: Supabase Primary 링크의 `yangsukeun's Project1`, `vgelnrycivorwczdqpsu`. CRM 추적 코드의 DB 호스트 검증과 기존 User/LeaveRequest/CsTool 테이블, CS 통합관리 링크를 읽기로 대조했다.
- `supabase_apply_migration`의 `cs_complete_test_isolated_storage` 작업은 자동 승인 검토에서 거절됐다. 이유: 이 원격 프로젝트가 승인된 CRM TEST 저장 대상이라는 명시적 대상 승인이 부족하다. 도구는 거절을 반환했으며 실행 성공 결과가 없다. 다른 경로로 우회하거나 재시도하지 않았다.
- 사용자에게 해당 프로젝트의 TEST 전용 3개 테이블 추가 여부를 명시적으로 질문했다. 답변 대기. 대상 승인 이후에만 새 근거에 따른 한 번의 재시도 및 적용 후 검증이 가능하다.

## 되돌리기

원격 DDL은 실행되지 않았으므로 현재 원격 롤백 대상이 없다. 적용 이후 코드 롤백은 기존 aa43e48로 기능을 되돌리되 새 TEST 테이블과 불변 원본/이력은 보존한다. 테이블 삭제/TRUNCATE로 롤백하지 않는다. TEST 내용 복귀는 기존 스냅샷 내용을 새 버전으로 저장하여 이력을 보존한다.
